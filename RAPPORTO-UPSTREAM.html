What this is asking for. The four defects in the first section are upstream bugs, reproduced on-device with logs and fixes. They are offered as bug reports. 1 · Defects found upstream

Data loss · highest

A failed store fetch deletes that store's library and its Steam shortcuts

What happened. A scheduled sync started while the Deck suspended. A socket does not age while the machine sleeps, so a request with timeout=30 surfaced its failure 14,596 seconds later. That is the accident. The defect is what followed.

[MicrosoftCatalog] /v2/titles unexpected TimeoutError
[MicrosoftCatalog] /v2/titles returned 0 titles in 14596.8s
[MicrosoftCatalog] /v2/titles returned 0 titles          (WARNING)
[SyncService] microsoft: 0 games
[SyncService] Saved library cache (140 games) to library_cache.json
[SyncService] sync complete — 140 games across 3 stores in 39282ms (0 errors)
[ShortcutService] (added=0 removed=603 ...)

Result: 603 Steam shortcuts deleted. Steam shortcuts went from 744 to 141. The run reported 0 errors throughout, and the loss was noticed days later by accident.

Root cause, at two independent levels.

  • microsoft_catalog._xcloud_titles_sync returns [] on every error branch — HTTPError, URLError, generic exception, non-JSON. A broken fetch therefore arrives downstream as "this account owns no Xbox games", indistinguishable from an empty library. This is why the run counted zero errors.
  • Independently, in core/sync_run_mixin.py the per-store loop assigns libraries[store.store_name] = games unconditionally. The errors dict is collected but only used for reporting. So even a correctly reported failure still empties that store. core/sync_service.py does the same for single-store refresh.

Steps to reproduce — no suspend needed: make _xcloud_titles_sync raise (block gssv-play-prod.xboxlive.com, or drop the network mid-sync), run a sync, observe the store's games and shortcuts disappear while the log reports success.

Fix applied in this fork. The catalogue raises a dedicated XCloudCatalogUnavailable instead of returning empty, so a failure stays a failure. The sync loop carries the previous library forward for any store that failed — a failed store may cost freshness, never data. A third guard warns (does not block) when a successful fetch returns less than half of what a store had, floored at 10 games so small libraries do not cry wolf. 10 tests cover it, including the inverse case: a genuinely shrinking library must still be recorded.

Every boot · easy fix

The config schema rejects a section the plugin itself writes

steam/current_user.py defines CONFIG_ACTIVE_USER_KEY = "steam.active_user" and both writes and reads it, explicitly supporting the nested form. The schema at config/schema.json has additionalProperties: false at the root and does not declare a steam section.

The result is that the plugin invalidates its own config and starts in degraded mode on every boot for any user who has an active Steam account recorded:

[Unifideck] config validation FAILED — starting in degraded mode.
1 error(s). First: : Additional properties are not allowed ('steam' was unexpected)

Validating the merged config (shipped defaults deep-merged with user overrides) gives 1 error before, 0 after adding the section. The fix is 11 lines of JSON and nothing else.

Latent · currently dead code

SteamBridge calls a Steam API that no longer exists

SteamBridge.getAppOverview() reads window.SteamClient.Apps.GetAppOverview. On current Steam that is undefined — verified over the CEF debugger against the live client. The method therefore returns null for every appid ever passed to it, and isReady(), which tests the same symbol, always returns false.

Impact today is nil: the only consumer, hooks/useSteamLibrary.ts, is exported from the barrel but imported by nothing and is tree-shaken out of the bundle. It is reported because it is a working-looking API that silently answers "no" to everything.

The live equivalent is window.appStore.GetAppOverviewByAppID(), which exists in SharedJSContext.

Type drift · note only

The frontend Game interface does not match the backend dataclass

core/types/domain.py has store_game_id, installed, exe_path, tags, and no id, is_installed or cover_image. The TS interface in types/api.ts declares the latter set. adaptGame in hooks/useGameInfo.ts bridges the two and its comment already documents the trap.

Any code consuming raw get_all_unifideck_games rows reads undefined silently. In this fork that shipped as three separate bugs before the type was corrected: an always-empty "Installed" filter, a grid of React children keyed undefined, and playtime lookups that never matched.

Flagged as a note rather than a patch: correcting the type surfaced five call sites and touching them all is exactly the kind of sweeping change CONTRIBUTING.md asks contributors not to make unsolicited.

2 · Steam integration facts worth documenting

These are not bugs — they are behaviours of current Steam that cost real time to discover, and that any code touching shortcuts will meet.

AreaFinding
Shortcut AppIDs They exist in two 32-bit readings. The backend and games.map use the signed form (-310337468); Steam's app store and its routes use the unsigned one (3984629828). Mixing them fails silently: GetAppOverviewByAppID(signed) returns null, and Navigate("/library/app/<signed>") matches no route and quietly lands the user on the library home page.
Cover art For non-Steam shortcuts, only appStore.GetCustomVerticalCapsuleURLs(overview)[0] — the .jpg — actually loads. The .png sibling, both /assets/…library_600x900.jpg forms from GetCachedVerticalCapsuleURL, and the CDN URL from GetVerticalCapsuleURLForApp all 404. Probed across five shortcuts.
appStore methods They are prototype methods that reach through this (GetCustomVerticalCapsuleURLs calls this.GetCustomImageURLs). Calling a detached reference throws TypeError, which a broad catch turns into "this game has no artwork". Call with the receiver.
Gamepad focus Steam does not move DOM focus when navigating with the pad. It marks the focused element with its own gpfocus class and gpfocuswithin on ancestors. :focus never matches during controller navigation, so any highlight keyed on it — or on React onFocus — stays invisible. Verify with document.querySelectorAll(".gpfocus"); a programmatic .focus() proves nothing about the pad.
Realms Plugin JS runs in SharedJSContext, which has appStore and SteamUIStore; the rendered DOM lives in the Big Picture window, whose realm has neither. Inspecting the wrong one yields confident false conclusions.
Viewport Gaming Mode renders at devicePixelRatio 1.5, so a 1280×800 panel is an 854×534 CSS viewport. Steam then draws its status bar (~38px) and button legend (~35px) over the route.
Analog triggers TRIGGER_LEFT/TRIGGER_RIGHT are delivered to onButtonDown. Nothing in the plugin bound them, so this was unverified; instrumenting on-device recorded 12 R2 and 5 L2 presses.

3 · Local changes, not proposed for merging

Two layers sit on top of upstream here. Neither is offered as a contribution; they are listed so the diff is fully accounted for.

Pre-existing on this device

Before any of the work above, this install had already replaced the /library tab injection with a standalone route. Five files: src/index.tsx (registers /unifideck instead of calling applyLibraryPatch, and does not start the collection manager), src/teardown.ts, src/views/QuickAccessPanel.tsx (adds a Library button), plus new src/views/UnifideckPage.tsx and src/lib/routes.ts. Steam's own library UI is left untouched by this arrangement.

Added in this fork

The standalone page was rebuilt because it reused components written for an injected tab and did not survive a 741-game library at full screen: every game mounted at once (741 tiles and 741 cover images in one commit), a native <select> and <input> that gamepad focus cannot reach, filters switching on onFocus, and a full re-filter and re-sort on every keystroke.

A small polyfill in a vitest setup file turns all three green. Whether they also fail in upstream CI is unknown, so this is mentioned rather than reported.

4 · Suggested order

  • The sync data loss first. It is silent, destructive, and reachable by anyone who suspends the Deck at the wrong moment. The two-level fix is small and covered by tests.
  • Then the schema section. Eleven lines, and it stops every affected install from booting degraded.
  • Then the dead Steam API, whenever convenient — harmless today, misleading whenever someone next relies on it.
Reported against Unifideck Release-0.7.3. Every log line, count and measurement above was taken from a live install, not inferred. Patches for the first two items exist and are running in production on that device; they are available on request rather than as an unsolicited PR, per CONTRIBUTING.md.
